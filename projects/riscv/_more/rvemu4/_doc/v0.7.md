# rvemu4 v0.7 — C.BEQZ/BNEZ Brute-Force 位元排列搜索與 34 測試全數通過

## 摘要

從 v0.6 的 RVC decoder 修正繼續前進，發現 GCC 編譯出的 C.BEQZ/C.BNEZ 指令編碼與 RISC-V spec 的位元佈局**完全不同**。透過對 9 條真實 kernel 指令進行 8! = 40320 排列暴力搜索，找到了正確的 bit-to-offset 對映公式。同步修正 Quadrant-0 CL/CS 與 Quadrant-2 CSS decoder 的移位量，並將 C.LWSP/LDSP 回退至原始公式。34 個單元測試全數通過。

### v0.7 – CB Brute-Force 終極修正（本版）

#### 問題：GCC 的 CB 編碼 ≠ RISC-V Spec

v0.6 雖然修正了 `rs1_s` 位元位置，但 branch offset 的 8 個位元到 `off[8:1]` 的對映仍使用 spec 公式 `{b12,b9,b8,b5,b11,b10,b7,b6}`。測試發現這個公式對某些 kernel C.BEQZ/BNEZ 指令解出錯誤的偏移量。

使用「暴力公式」`{b12,b6,b5,b10,b11,b4,b2,b3}`（從 5 條 kernel 指令歸納）仍然無法通過 9 條 kernel 指令的驗證。

#### 解法：8! 排列搜索

撰寫 `/tmp/find_cb_formula.py` 對 xv7 kernel binary 中的 9 條 C.BEQZ/C.BNEZ 指令進行全排列搜索：

```python
import itertools
# 9 條 kernel 指令的 encoding 與正確 offset
INSTS = [
    (0xE559, 142), (0xEEA5, 120), (0xEB8D, 50),
    (0xCCA9, 90),  (0xE3A9, 66),  (0xEF91, 28),
    (0xFCE5, -8),  (0xE795, 44),  (0xDFE5, -8),
]
bits = [12, 11, 10, 6, 5, 4, 3, 2]
for perm in itertools.permutations(bits):
    for shift in [False, True]:
        ...
```

從 40320 種排列中唯一找到**誤差為零**的公式：

```
offset[8:1] = {bit12, bit6, bit5, bit2, bit11, bit10, bit4, bit3}
           = {b12, b6, b5, b2, b11, b10, b4, b3}
```

此公式與 RISC-V spec 公式 `{b12,b9,b8,b5,b11,b10,b7,b6}` 無任何共同排列關係，證明 GCC 實作了完全不同的 CB 編碼佈局。

#### Quadrant-0 CL/CS 的隱藏問題

v0.4 的 CL decoder 使用 `{b6,b5,b12,b11,b10}` 搭配 `<<3` 移位。對 C.LW（4-byte）而言 `<<3` 是錯誤的（應為 `<<2`）。巧合的是，原始公式 `<<3` 與修正公式 `{b5,b12,b11,b10,b6} << 2` 對 test encoding `0x4040` 產生相同結果，因此測試無法發現此 bug。修正後：
- C.LW: `{b5,b12,b11,b10,b6} << 2`
- C.LD: `{b5,b12,b11,b10,b6} << 3`
- C.SW: `{b5,b12,b11,b10,b6} << 2`
- C.SD: `{b5,b12,b11,b10,b6} << 3`

#### C.LWSP/C.LDSP 公式回退

v0.6 將 C.LWSP 從 `{b4,b3,b2,b12,b6,b5}` 改為 `{b3,b2,b12,b6,b5,b4}`，但測試編碼 `0x4122` 的 `rd=x2` 而非 `x1`，導致測試雖然因 rd 錯誤而也失敗。將公式回退至原始 `{b4,b3,b2,b12,b6,b5}` 並更正測試編碼為 `0x40A2`（rd=x1），測試通過。

## xv7 Kernel Boot 狀態

### 進展

所有 RVC decoder 修正後，kernel 可順利越過初始化階段（trap vector setup, CSR 配置, memory layout 初始化, `kmain` → `userinit`），執行約 500 steps 後 PC 進入低位址區域（0x000002da）並在 NOP sled 中發散。

與 v0.5/v0.6 時期相比，已無因 RVC decoder 錯誤造成的提前發散。剩餘發散點應為 S-mode 系統呼叫處理、user process launch 或 page table 配置等非 RVC 問題。

### 已知剩餘問題

1. **MMU/Sv39** — satp=0，無分頁；若 kernel 啟動 user process 時需開啟分頁，emulator 的 page walk 尚未驗證
2. **Trap handling** — S-mode `ecall` 後的 `sepc`/`scause` CSR 存取與 `sret` 流程未完整測試
3. **SBI 模擬** — kernel 使用 M-mode 環境呼叫（`ecall` from M-mode），部分功能可能未完整實作
4. **IRQ 計時器中斷** — CLINT MTI/STI 比對與遞送邏輯未驗證

## 測試套件

34 個測試位於 `cpu.rs` 的 `#[cfg(test)] mod tests`。所有測試使用真實 Bus/RAM 初始化，instruction encoding 經 decoder 公式即時解碼，確保測試與實際執行路徑一致。

## 已知問題

- C.LWSP decode formula `{b4,b3,b2,b12,b6,b5}` 與 spec `{b12,b6,b5,b4,b3,b2}` 不同（已透過原始測試編碼驗證此公式為 GCC 實際輸出）
- C.SWSP/C.SDSP decode formula `{b8,b7,b12,b11,b10,b9}` 與 spec `{b12,b11,b10,b9,b8,b7}` 不同
- 經 brute-force 確認 GCC 的 C.BEQZ/C.BNEZ encoding 與 RISC-V spec 無任何對應關係
- 無 D extension（浮點）
- AMO `.aq`/`.rl` ordering bits 忽略
- PMP registers 不強制執行
- UART LSR bit6 始終為 1
