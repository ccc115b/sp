# single_cycle v0.3 — RVC + ECALL + ELF loader

讓單週期 CPU 能執行 `riscv/rv4/examples/` 下的範例（`hello.o`, `fact.o`, `fib.o`, `sum.o`），透過 `.o → .hex` 轉換流程。

## 現狀分析

所有範例皆由 Rust nightly 編譯，目標 ISA 為 `rv64i2p1_m2p0_a2p1_c2p0`，**大量使用 RVC（壓縮指令）**。以下為各範例使用的指令統計：

| 範例 | 檔案大小 | RVC 指令佔比 | 特殊需求 |
|------|---------|-------------|---------|
| hello.o | 26 bytes code | ~100% | C.J, C.LI, C.MV, ECALL, unimp |
| fact.o | ~100 bytes code | ~90% | C.ADDI16SP, C.SD, C.SW, C.SUB, C.JR, MUL, DIVU |
| fib.o | ~46 bytes code | ~90% | 同上 + C.LUI, C.ADDIW |
| sum.o | ~46 bytes code | ~90% | 同上 |

完整指令清單（32-bit + 16-bit）：

| 類別 | 指令 |
|------|------|
| RV64I 32-bit | ADDI, AUIPC, ECALL, JALR, LUI, SB, SD, SW |
| RV64M 32-bit | MUL, DIVU, SUB, OR, NEG (SUB x0), ADD, NEGW |
| RVC Q0 | C.ADDI4SPN, C.LW, C.LD, C.SW, C.SD |
| RVC Q1 | C.ADDI, C.LI, C.ADDI16SP, C.LUI, C.SRLI, C.SRAI, C.ANDI, C.SUB, C.XOR, C.OR, C.AND, C.J, C.BEQZ, C.BNEZ |
| RVC Q2 | C.SLLI, C.LWSP, C.LDSP, C.SWSP, C.SDSP, C.JR, C.JALR, C.MV, C.ADD, C.NOP (0x0000), C.EBREAK |

## 須實作項目

### 1. RVC 壓縮指令解碼

#### 指令取得機制改造
- 將 `imem` 改為 `reg [15:0] imem [0:2047]`（16-bit 寬度），或保留 32-bit 但改以 halfword 粒度讀取
- 新增 `is_compressed` 判斷：`instr_low & 0x3 != 0x3` 則為 16-bit
- PC increment：16-bit 指令→+2；32-bit 指令→+4
- 所有 PC 相關的訊號（`pc_plus4`、`imm_j` 目標、`imm_b` 目標等）需支援半字組對齊
- `pc[11:2]` → `pc[12:1]`（16-bit 粒度）

#### 解碼邏輯

RVC 分為三個 quadrant，由 `instr[1:0]` 選擇：

```
Quadrant 0 (00):  Register-pair (x8–x15) 類
  - C.ADDI4SPN → rd' = sp + imm
  - C.LD / C.SD → load/store 雙字 (RV64)
  - C.LW / C.SW → load/store 字

Quadrant 1 (01):  標準運算與跳躍類
  - C.ADDI → rd = rd + imm
  - C.ADDIW → rd = sext(rd[31:0] + imm) (RV64)
  - C.LI → rd = imm
  - C.ADDI16SP → sp = sp + imm×16
  - C.LUI → rd = imm << 12
  - C.SRLI/C.SRAI → srli/srai rd', shamt
  - C.ANDI → rd' = rd' & imm
  - C.SUB/C.XOR/C.OR/C.AND → rd' op rs2'
  - C.J → PC += imm
  - C.BEQZ/C.BNEZ → if rd' ==/!= 0 branch

Quadrant 2 (10):  SP-relative 與暫存器類
  - C.SLLI → rd = rd << shamt
  - C.LWSP/C.LDSP → rd = M[sp + imm]
  - C.SWSP/C.SDSP → M[sp + imm] = rs2
  - C.JR → PC = rs1 & ~1 (若 rs1≠0, rs2=0)
  - C.JALR → ra=PC+2, PC=rs1 & ~1 (若 rs1≠0, rs2=0)
  - C.MV → rd = rs2 (若 rs1=0, rs2≠0)
  - C.ADD → rd += rs2 (若 rs1≠0, rs2≠0)
  - C.NOP (若 rs1=0, rs2=0, funct3=0) → 等於 `0x0000`
  - C.EBREAK (若 rs1=0, rs2=0, funct3=1, bits[12]=1) → `0x9002`
```

#### 控制單元擴充
- 新增 `is_compressed` 訊號（由 opcode 階段前置偵測）
- RVC 指令不走原本的 opcode/funct3/funct7 解碼路徑
- 改以獨立的 `exec_compressed` 組合邏輯區塊處理所有 RVC 操作
- RVC 指令的暫存器編號需對應 `x8–x15`（`rd'`/`rs1'`/`rs2'`）或 `x0–x31`

### 2. ECALL 與 Trap 機制

#### CSR 擴充
```
mepc   (0x341):  trap 發生時的 PC
mcause (0x342):  trap 原因（ecall from M-mode = 11）
```

#### ECALL 指令處理
- 編碼：`0x00000073`（opcode=0x73, funct3=000, funct12=0x000）
- 執行時：
  1. `mepc <= pc`（保存回歸位址）
  2. `mcause <= 11`（ecall from M-mode）
  3. `pc <= mtvec`（跳躍至 trap handler）

#### 軟體 Trap Handler（在 testbench / .hex 中）
Trap handler 位於 `mtvec`，檢查 `mcause` 後分派：
```
trap_handler:
    csrr t0, mcause
    li   t1, 11
    bne  t0, t1, .Lunknown
    # ecall from M-mode
    li   t0, 0
    csrw mcause, t0       # 清除 mcause
    # 根據 a7 (x17) 分派：
    beqz a7, .Lexit        # a7=0: exit
    li   t0, 1
    beq  a7, t0, .Lputchar # a7=1: putchar
    li   t0, 2
    beq  a7, t0, .Lputs    # a7=2: puts
```

但 trap handler 本身需用軟體實作，無法放在硬體內。替代方案有兩種：

**方案 A：硬體輔助，軟體 handler**（較接近真實 RISC-V）
- 在 `program.hex` 中加入 trap handler 程式碼
- `mtvec` 指向 handler 位址
- Handler 使用 CSR 指令讀寫 mepc/mcause，處理完後 `mret` 回原程式

**方案 B：純硬體 ECALL 處理**（適合單週期教學目的）
- 在 CPU 內部直接處理 `a7=0/1/2` 三種系統呼叫
- 不經由 trap 機制，直接修改記憶體/輸出行為
- 方案較簡單但偏離 RISC-V 規格

**建議：方案 A**，可同時驗證 CSR 與 trap 機制的完整性。

#### MRET 指令
- 支援 `mret`（`0x30200073`）：`pc <= mepc`
- 需在控制單元中新增 `mret` 判斷（opcode=0x73, funct3=000, funct12=0x302）

### 3. ELF 連結與 .hex 轉換

#### ELF .o 檔案特性
- Type: REL（relocatable），非 EXEC
- 包含 `.text` 與 `.rodata` section
- 包含 `R_RISCV_PCREL_HI20` 與 `R_RISCV_PCREL_LO12_I` 兩種 relocation
- 無 program header，無法直接載入

#### 轉換方案

建立 `riscv64-unknown-elf-ld` + `objcopy` 為基礎的 bash 腳本，或撰寫 Rust/Python 的簡易連結器：

```
方案一：現成工具鏈
  riscv64-unknown-elf-ld -T link.ld -o out.elf hello.o
  riscv64-unknown-elf-objcopy -O binary out.elf out.bin
  python3 bin2hex.py out.bin > program.hex

方案二：自製最小連結器
  讀取 ELF section + relocation table
  將 .text 與 .rodata 配置到連續位址空間
  解析 R_RISCV_PCREL_HI20/LO12_I 並修補指令
  輸出 flat binary → .hex
```

**建議：方案一**，使用現有 linker script（參考 `mini-riscv-os/os.ld`）快速達成。

#### 最小 Linker Script (`link.ld`)

```
OUTPUT_ARCH(riscv)
ENTRY(_start)
SECTIONS {
    . = 0x00000;
    .text : { *(.text) *(.text.*) }
    .rodata : { *(.rodata) *(.rodata.*) }
    .bss : { *(.bss) }
    _end = .;
}
```

#### 記憶體配置
- 指令記憶體：位址 `0x00000` 開始（目前 `imem[0:1023]`，4KB）— 需增大至 8KB 以上
- 資料記憶體：8KB 維持不變（`dmem[0:8191]`）
- 堆疊：`sp` 設於資料記憶體末端（`0x02000` 或 `0x01FF0`）

### 4. 其他缺失指令

| 指令 | 編碼 | 說明 | 目前已支援 |
|------|------|------|-----------|
| NEG | SUB rd, x0, rs | 負數 | ✓ (SUB) |
| NOP | ADDI x0, x0, 0 | 空操作 | ✓ (ADDI to x0) |
| C.NOP | `0x0000` | 壓縮空操作 | ✗ |
| C.EBREAK | `0x9002` | 除錯中斷 | ✗ |
| MRET | `0x30200073` | Trap 返回 | ✗ |

C.NOP 與 C.EBREAK 的處理：
- C.NOP（`0x0000`）：在 RVC Q2 funct3=0 中，若 `rs1=0, rs2=0` → NOP
- C.EBREAK（`0x9002`）：在 RVC 中編碼為 C.EBREAK，可視為 `ecall a7=0` 並停止模擬

### 5. 測試流程

```bash
cd single_cycle

# 1. 連結 .o → .elf → .bin → .hex
riscv64-unknown-elf-ld -T link.ld example.ld -o ex.elf \
  /path/to/rv4/examples/hello.o
riscv64-unknown-elf-objcopy -O binary ex.elf ex.bin
python3 bin2hex.py ex.bin > program.hex

# 2. 編譯模擬
iverilog -o single_cycle_tb -g2012 rv64i_cpu.v tb_rv64i.v
vvp single_cycle_tb

# 預期輸出：
#   Hello, World!
#   ##### PASS #####
```

### 6. 其他注意事項

#### imem 容量擴充
- 目前 `imem [0:1023]` × 4 bytes = 4KB
- fact.o 約 100 bytes code + 200 bytes rodata，仍在範圍內
- fib.o/sum.o 更小
- 但 `hello.elf` 含 linker 產生的符號表時約 5KB
- **建議**：將 `imem` 擴充至 `[0:4095]`（16KB），`pc` 位址範圍相對應調整

#### PC 對齊
- RVC 允許 PC 在奇數位址（但 RV 規格要求 halfword 對齊，即 LSB=0）
- 目前 `pc[11:2]` 索引假設 4-byte 對齊 → 需改為 `pc[12:1]` 使用 16-bit 寬度
- **設計方案**：指令記憶體改為 `reg [15:0] imem [0:2047]`，讀取 16-bit，再視需要組合第二個 halfword

#### 資料記憶體 aliasing
- 目前資料記憶體從 `alu_result[12:0]` 索引，上限 8KB
- 若程式碼在 `0x00000`、資料在 `0x02000`，需確保兩者不重疊
- **方案**：將資料記憶體基底設為 `0x02000` 或使用絕對位址映射

#### 效能估算
- hello.o：約 5 條指令 → 5 cycles（含 1 ECALL + 1 終止）
- fact(10)：約 40 條指令 → 200+ cycles
- fib(20)：約 30 條指令 → 150+ cycles
- sum(100)：約 400 條指令 → 2000+ cycles
- testbench 的循環次數需大幅增加（`for (i = 0; i < 5000; i++)`）
